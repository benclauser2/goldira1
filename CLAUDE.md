# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Gold IRA Blueprint" — single-page marketing/lead-gen landing page built from a Figma design. No build step, no package manager, no tests, not a git repo. Three files: `index.html` (markup + inline SVG icon sprite), `css/styles.css`, `js/reviews.js` (review data) + `js/main.js` (loaded at end of `<body>`, in that order). CSS `url()`s are relative to `css/`, so they use `../images/`.

Run: open `index.html` in a browser, or serve the folder (e.g. `npx serve .` / `python -m http.server`) so relative image paths and `ResizeObserver`/`dialog` behave like production.

## Images

All images live in `images/`, kebab-case, prefixed by the page section they belong to (`hero-*`, `step-*`, `portfolio-*`). When new Figma exports arrive with raw names, rename to this convention. `initImageFallbacks()` adds `.is-missing` to any broken `<img>` so layout holds.

## Code structure

**CSS** (`css/styles.css`) is split into numbered sections that mirror page order (`/* ===== N. Name ===== */`): 1 design tokens (`:root` custom properties from Figma — colors, three font stacks `--font-display`/`--font-body`/`--font-ui`, radii, `--container`, `--gutter`, `--section-y`, `--shell-max`/`--shell-gutter` for header+footer, `--error`, `--hover-warm`), 2 base, 3 shared components, then 4–19 one per page section (header, hero+growth calculator, reviews, what-is, how-it-works+situation check, eligible assets + who manages them, next-step band, gold IRA vs traditional IRA table + timelines (`.process`, `.process--4`), 12 long-form guide components, then why, protection, knowledge base, guide, FAQ, team, footer+policy dialog). Add new styles to the matching section; use existing tokens rather than raw values. Breakpoints in use: 1100, 1024, 900, 768, 640, 560px (desktop-first `max-width`). Nav collapses to mobile menu at ≤900px (JS matches `min-width: 901px`).

**JS** (`js/main.js`) is one IIFE with `$`/`$$` query helpers and one `initX()` per feature, called at the bottom:
- `initHeader` — solid header after 40px scroll (rAF-throttled), mobile menu toggle swapping sprite `#i-menu`/`#i-close`, Esc closes.
- `initGrowthCalc` — hero savings calculator (`#growth-calc`): three range sliders → `futureValue()` (monthly compounding, end-of-month deposits). Markup ships with the default result pre-rendered ($500 × 15 yrs @ 5% = $133,644) so it reads correctly without JS.
- `initReviews` — renders `REVIEWS` (js/reviews.js: 177 reviews copied verbatim from goldirablueprint.com/reviews/) into `#reviews-track` by cloning `<template id="review-template">` (text via `textContent` only). `renderRatingSummary()` computes average/count from `rating`; always-visible category chips (`data-filter` = review `category`, same keys as the source site, e.g. Fixed Income = `modest-income`, Tradesmen = `blue-collar`); `initCarousel()` drives the scroll-snap track with arrows, dots, or a "3 / 59" counter above `CAROUSEL_MAX_DOTS` pages. Page indicators only update after scrolling settles (`SCROLL_SETTLE_MS`): changing layout mid-scroll makes mandatory scroll-snap re-snap and cancels smooth scrolling.
- `initSituation` — checkbox picks render cards from `SUGGESTIONS` map; submit copies picks into `#guide-form`'s hidden `situation` field and scrolls to `#guide`.
- `initLeadForms` — generic handler for every `form[data-lead-form]` (next-step, guide, footer). Custom accessible validation (`novalidate` + `checkValidity`, `.field__error` injected with `aria-describedby`/`aria-invalid`); inputs must have class `.field__input` inside a `.field`. On success hides form and focuses the **next sibling** `.form-success`. Network call is isolated in `submitLead(payload)` — currently only `console.info`s; wire the real endpoint (e.g. GHL webhook) there and throw on failure (the handler re-enables the button).
- `initTablist` — shared ARIA tabs (roving tabindex, Arrow/Home/End) used by the knowledge base and the FAQ tabs.
- `initKnowledgeBase` — filters `.kb-card` by space-separated `data-topics` against tab `data-filter`; prev/next arrows for the tab strip (prev overlays left edge, shown only once scrolled).
- `initReadMore` / `refreshReadMore` — `[data-readmore="<id>"]` buttons expand line-clamped text; buttons auto-hide when text doesn't overflow. Re-run `refreshReadMore()` after anything that changes visibility/layout. Used by the hero intro (`#hero-lede`, 4 lines); on dark backgrounds add `.read-more--on-dark` (gold, for contrast).
- `initStatCounters` — hero stats count up from 0 when scrolled into view (parses prefix/number/suffix from each `<strong>`, so edit the numbers in HTML only). Width locked after `document.fonts.ready`; skipped under `prefers-reduced-motion`.
- `initStatTips` — info-icon tooltips on the hero stats (`.stat-tip`, `role="tooltip"` + `aria-describedby`). Hover/focus are CSS; tap toggles `aria-expanded`; Esc or an outside tap closes (Esc also suppresses hover/focus via `.is-dismissed`). Tooltip copy is placeholder (TODO in HTML).
- `initPolicies` — footer `[data-policy]` buttons open the native `<dialog>`; `POLICIES` copy is a TODO.

JS style: every `initX()` returns early if its root elements are missing (one removed section must not break the rest); build DOM with the `createEl(tag, props, children)` helper; name magic numbers as constants at the top. Base resets use `:where()` (zero specificity) so component class rules always override them — keep new resets that way. Conventions: toggle visibility with the `hidden` attribute (CSS forces `[hidden]{display:none!important}`), build dynamic DOM with `textContent` (never interpolate data into `innerHTML`), semantic landmarks with `aria-labelledby` on each section, icons via the inline Lucide SVG sprite (`<use href="#i-...">`).

## Hero must fit the first screen (desktop)

On desktop (≥1025px wide) the whole hero (copy, calculator, stats row) must be visible without scrolling down to a 625px-tall viewport (1366×768 laptop minus browser chrome). Two height media queries in CSS section 5 do this: `max-height: 1000px` (height-scaled spacing, 3-line intro, compact calculator) and `max-height: 680px` (2-line intro, tighter calculator). The calculator is usually the taller column, so trim it first. Re-measure after any hero content change. Phones/tablets stack the hero and are exempt.

## Page content source

Page copy follows the client's content brief ("GoldIRA September 2026.pdf"). Sections not in the brief (next-step band, Why, Portfolio protection, Knowledge base, Free guide, FAQ, Team) are **commented out in `index.html`, not deleted**. Their CSS/JS stays and every `initX()` no-ops when its markup is missing. Uncommenting needs nav/footer links restored. HTML comments can't nest, so a section must contain no `<!-- -->` before it is commented out.

"What Happens to a Gold IRA After the Owner Retires?" has its own section (`#after-retirement-section`, H3) right above the FAQ; it is not a FAQ item. From the custodian services label to the end of the brief, questions live in `#gold-ira-faq` as the spec's "FAQ Labeled Tabs": the three spec Labels are the tabs (`#gold-ira-faq-tabs`) and each panel keeps the old anchor id (`#custodian-services`, `#account-monitoring`, `#beneficiaries`). Every question is a native `<details class="faq-item">` accordion with the spec heading level (H2–H4) inside `<summary>`; the first accordion in each tab ships with `open`. `initFaq()` drives any `.faq [role="tablist"]`; when a link, `hashchange`, or the arrival URL targets a panel or question, it opens the tab and expands the accordion. The two `.money-guide` asides ("Understanding Gold IRA Money" between `#funding` and `#fund-gold-ira`; "Funding and Understanding a Gold IRA", `.money-guide--mirror`, between `#after-retirement-section` and the FAQ; full-width bands, content in `.money-guide__inner`) are client-supplied summary copy, not part of the brief; its titles repeat spec headings, so they are `<p>`/`<dt>`, never headings. Long-form brief content uses three shared components (CSS section 12): `.step-list` (numbered steps, one column), `.fact-list` (`<dl>` "Term: text" rows), and `.section-head--prose` (paragraph-only answers; wider, but centered like all section heads). Heading levels come from the SEO spec sheet ("HSD // Content Sprints / Main / Template - Gold Ira Money"): one H1 (hero), then each brief heading uses exactly the spec's H2/H3/H4, independent of visual size (`.section-title`, `.section-title--sm`). Spec H2s start a new `<section>` (backgrounds alternate white/grey); H3/H4 are `.section-head--sub` blocks inside it. Titles inside lists/cards (`.step-list__title`, `.card-title`) are one level below their block's heading, so the outline never skips a level. Text that isn't in the spec outline (hero point titles, calculator title, reviews heading, review card titles) is `<p>`, not a heading. Yellow-highlighted phrases in the brief are internal-link anchor text; their targets are TBD.
